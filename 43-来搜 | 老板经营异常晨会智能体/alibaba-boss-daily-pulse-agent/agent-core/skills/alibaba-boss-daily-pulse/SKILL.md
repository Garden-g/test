# 老板经营异常晨会

## 目标

每天早上用最近可用的真实经营数据，告诉老板：

1. 今天最需要先处理什么；
2. 发生了什么；
3. 为什么；
4. 怎么解决；
5. 下午或明天如何复查。

最终 XLSX 不是后台巡检表，也不是模块数据汇总。原始数据保存在当前 Run 的 JSON
中，所有可见事实必须先经过运营专家 LLM 诊断。

## 核心原则

- 永远先 search 工具再 call，确认实时工具名和 schema。
- 默认只读，只采集、诊断、排序和生成行动建议，不直接修改后台。
- 不把“今天数据未出”误判为经营归零；先找最近完整日，再用最近 7 天作基线。
- 首页最多 3 个问题；异常诊断最多 15 个问题组；今天行动最多 8 个。
- 相同根因的商品、广告组、关键词、客户或渠道必须合并，代表对象最多 3 个。
- 每个可见问题必须有关键证据、运营专家判断、核心原因和解决方案。
- Sheet 名和表头使用自然中文，不展示 P0/P1、Backlog 或技术黑话。
- 不展示原始 JSON、工具名、字段名、技术错误或完整数据覆盖清单。

## 时间口径

| 用户说法 | 默认口径 |
|---|---|
| 老板晨会、早上看一下、今天先看异常 | 优先今天 00:00 至当前；当天未就绪时使用最近完整日，并拉最近 7 天基线。 |
| 今天店铺哪里不对 | 今天至当前 + 最近 7 天对照。 |
| 昨天复盘 | 昨天全天。 |
| 本周经营异常 | 本周一至最近完整日，并用上一个完整周作背景。 |
| 最近 7 天、近一周 | 滚动最近 7 天。 |
| 明确日期区间 | 严格按用户给定区间。 |

周期、数据时效和对象范围只在第一张 Sheet 写一次，不在其他 Sheet 重复。

## 核心采集

先 search，再按可用性调用：

| 经营模块 | 只读能力与要点 |
|---|---|
| 店铺诊断 | `store_diagnose_brief`，只作为总入口，不原样复制摘要。 |
| 经营大盘 | `data_advisor_shop_summary`，采曝光、点击、访客、询盘和下单漏斗。 |
| 流量渠道 | `data_advisor_shop_channel`、`data_advisor_shop_flow`。 |
| 商品效率 | `data_advisor_shop_product`，找高曝光低点击、高点击低询盘和主推商品异常。 |
| 区域市场 | `data_advisor_shop_region`。 |
| 服务 | `query_seller_shop_dim_diag_data`、`query_seller_acct_dim_diag_data`。 |
| 广告 | `icbu_ads_hateoas_query` 先查 company，再查 diagnosis；不能把外层成功当业务可用。 |
| 风控 | `shop_risk_diagnosis`。 |

按异常信号再补采访客、员工经营、交易合同、服务周报或质检明细。补采只用于解释
重要问题，不做无目标全量展开。

商品工具 `pageSize` 最大 20，默认至少查前 3 页或直到短页/无新增，记录总数、
采集数、排序和截断范围。不能把第 1 页当全店。

## 执行流程

1. 使用当前 Accio 对话 Run 已分配的目录：
   - 原始返回写入 `raw/`；
   - facts package、诊断 JSON 和 XLSX 写入 `outputs/`；
   - 不读取其他对话目录。
2. 解析时间范围和晨会对象；默认口径足够时不要追问。
3. 制作采集计划并逐项 search。search 不到的能力不 call，继续采其他模块。
4. 先采店铺、大盘、渠道、流量、商品和区域，再采风控、广告和服务。
5. 根据异常信号补采访客、员工、交易、服务周报或质检证据。
6. 整理 `outputs/daily_facts_package.json`，只保留：
   - 周期与数据时效；
   - 模块事实和对照；
   - 异常候选与代表对象；
   - 数据限制对经营判断的影响。
7. 读取 `references/diagnosis_prompt.md`，以国际站运营专家 LLM 身份重新诊断
   facts package，保存为 `outputs/boss_daily_pulse_diagnosis.json`。
8. 审核诊断：
   - 首页 1 至 3 个问题；
   - 每行有证据、专家判断、原因、方案和复查标准；
   - 同根因对象已合并；
   - 行动不超过 8 个；
   - 没有占位词、原始字段或虚构负责人。
9. 审核失败时只重写失败行 1 次；仍失败就停止交付，不能退回数据搬运版。
10. 生成 XLSX：

   ```bash
   /usr/bin/python3 <skill_dir>/scripts/build_xlsx.py \
     <OUTPUT_DIR>/boss_daily_pulse_diagnosis.json \
     <OUTPUT_DIR>/老板经营异常晨会_<YYYY-MM-DD>.xlsx \
     --period <周期> \
     --company <店铺或公司范围>
   ```

11. 补采或修正任何事实后，重新执行 LLM 诊断、构建和全部校验。

## 运营专家诊断规则

- 先按“今天不处理会损失什么”排序，不只按数值大小排序。
- 风控、交易/询盘链路中断、广告浪费和主推商品承接问题优先。
- 指标是证据，不是结论；不能只看到 0 或下降就直接定性。
- 单一证据只能写“优先验证的原因”，不能强行写成确定因果。
- 风险与机会都必须给出具体原因、今天动作和复查标准。
- 不写“加强运营、优化服务、提升转化、持续关注”等空话。
- 解决方案必须回应同一行的根因。

## 负责人和缺失字段

- `owner_name` 只能复制真实数据返回的姓名。
- 无真实姓名时：
  - 店铺、流量、广告、关键词、商品动作写 `运营`；
  - 询盘、客户、报价、跟进动作写 `业务`；
  - 无法可靠归类时，省略负责人字段。
- 只有店铺级服务数据时不能点名业务员。
- 获取不到、为空或不影响结论的字段直接删除。
- 只有缺失数据直接阻断某项经营判断时，才在首页底部写一条业务化数据限制，
  最多 3 句。
- 最终 XLSX 不显示 `未返回`、`待确认`、`不可判断` 或技术性覆盖明细。

## XLSX 结构

默认生成 `outputs/老板经营异常晨会_<YYYY-MM-DD>.xlsx`，固定只包含：

| Sheet | 内容 |
|---|---|
| `今天先看` | 一句话结论；最多 3 个“发生了什么、核心原因、解决方案、复查标准”。 |
| `异常原因` | 最多 15 个合并问题组；每行都有证据、专家判断、原因和方案。 |
| `今天行动` | 最多 8 个根因级动作；负责人只显示真实姓名、运营、业务或省略。 |

不创建数据覆盖、P0/P1、机会窗口、模块看板、会议议程等独立 Sheet。

## 缺数据策略

- 当天数据为空时先找最近完整日和最近 7 天，不能写“今日无曝光/无询盘”。
- 订单或金额缺失时，不判断 ROI 或成交转化。
- 广告消耗缺失时，不判断浪费金额，只能根据其他真实证据描述风险。
- 只有摘要没有明细时，可以给方向性建议，但不能编造客户、商品、订单或员工行为。

## 禁止动作

- 禁止调用发送、发布、编辑、删除、上传、扣费、生成素材或修改配置的工具。
- 禁止直接调整广告预算、编辑商品、发送客户消息或处理待办。
- 用户要求执行后台动作时，只生成待人工确认的动作草案；本技能保持只读。
- 禁止向最终用户暴露凭据、内部执行环境或原始调用链路。

## Excel 安全与交付

构建器必须完成 LibreOffice headless 重存、清理 table/drawing 残留，并通过
`unzip -t`、`openpyxl.load_workbook()` 和包内残留扫描。任一步失败都不交付。

最终回复：

```markdown
已生成：[老板经营异常晨会_<YYYY-MM-DD>.xlsx](outputs/老板经营异常晨会_<YYYY-MM-DD>.xlsx)

老板结论：<diagnosis.executive_conclusion>
今天先做：<actions 中最重要的动作>
数据限制：<只有确实影响判断时才写>
```
