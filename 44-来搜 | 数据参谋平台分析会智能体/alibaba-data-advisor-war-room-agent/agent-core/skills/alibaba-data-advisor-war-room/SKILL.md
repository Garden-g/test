# 数据参谋平台分析会

## 目标

把数据参谋真实返回转成老板能直接决策的经营诊断，而不是后台指标搬运。
最终必须先回答：

1. 发生了什么；
2. 为什么；
3. 怎么解决；
4. 怎么复查。

原始指标、完整商品明细、访客明细和采集状态保存在当前 Run 的 JSON 文件中，
供追溯和 LLM 诊断使用，不放进最终 XLSX。

## 核心原则

- 默认只读，不发送消息、不改商品、不发布页面、不改广告、不消耗额度。
- 所有进入 XLSX 的事实必须先经过运营专家 LLM 诊断。
- 确定性脚本只负责采集、计算、排序和格式化，不能直接生成老板结论或机械任务。
- 首页最多 3 个问题；第二张 Sheet 最多 15 个问题组；行动最多 8 个。
- 相同根因的商品、关键词、国家、账号、访客或渠道合并成一个问题组，代表对象最多 3 个。
- Sheet 名和表头使用自然中文，不使用赛马、手术台、作战看板、Backlog、P0/P1 等黑话。
- 不编造数据、客户、负责人或目标结果。
- 不把工具名、参数名、原始 JSON、错误栈或内部执行细节写入最终 XLSX。

## 时间口径

| 用户说法 | 默认周期 |
|---|---|
| 一周、最近一周、近 7 天、平台分析会 | 最近 7 个完整自然日；存在 T-2 延迟时截止到最近完整日。 |
| 本周、这周 | 本周一到最近完整日；周内不足时用最近 7 天补背景。 |
| 上周 | 上一个完整自然周，周一到周日。 |
| 明确日期区间 | 严格使用用户给定日期。 |

周期和时效只在第一张 Sheet 展示一次，不在每个 Sheet 重复。

## 数据参谋能力面

先读取 `references/data_advisor_tools.md`，再按实时 search/call schema 制定采集
计划。reference 与实时 schema 冲突时，以实时 schema 为准。

| 模块 | 工具 |
|---|---|
| 店铺大盘 | `data_advisor_shop_summary` |
| 团队账号 | `data_advisor_account_summary` |
| 流量结构 | `data_advisor_shop_flow` |
| 渠道分布 | `data_advisor_shop_channel` |
| 地域市场 | `data_advisor_shop_region` |
| 商品表现 | `data_advisor_shop_product` |
| 访客明细 | `data_advisor_visitor_detail` |
| 流量画像 | `data_advisor_shop_flow_profile` |
| 竞品流向 | `data_advisor_to_product` |
| 类目推断 | `data_advisor_category_infer` |
| 类目预测 | `data_advisor_category_prediction` |
| 子类目排行 | `data_advisor_industry_cate_rank` |
| 国家排行 | `data_advisor_industry_country_rank` |
| 机会发现 | `data_advisor_opportunity_discovery` |
| 选品推荐 | `data_advisor_product_selection` |

工具 search 不到、无权限或没有业务数据时记录在事实包中，不猜参数，也不把空返回
写成 0。

## 执行流程

1. 使用当前 Accio 对话 Run 已分配的目录：
   - 15 个工具原始返回写入 `raw/`；
   - facts package、诊断 JSON 和最终 XLSX 写入 `outputs/`；
   - 不读取其他对话目录。
2. 解析会议目标、周期、店铺范围和指定行业/国家。默认口径足够时不要追问。
3. 采集本店大盘、账号、流量、渠道、地域、商品、访客、画像和竞品流向。
4. 确定真实主营类目，再采国家排行、子类目排行、机会发现和选品推荐。
5. 商品工具 `pageSize` 最大 20；精确历史周按自然日分页采集并聚合。默认至少
   取前 3 页或直到短页/无新增，记录总数、采集数、排序和截断范围。不能把第 1 页
   20 条当全店。
6. 把原始返回整理成业务 facts package，只保留：
   - 周期与数据时效；
   - 数据覆盖对判断的影响；
   - 店铺、账号、流量、渠道、地域、商品和访客事实；
   - 竞品流向、行业机会和选品背景；
   - 已知限制。
7. 读取 `references/diagnosis_prompt.md`，以国际站运营专家 LLM 身份重新诊断
   facts package，保存为 `<OUTPUT_DIR>/diagnosis.json`。
8. 审核诊断 JSON：
   - 首页 1 至 3 个问题；
   - 每个问题都有证据、专家判断、核心原因、解决方案和复查标准；
   - 同根因对象已合并；
   - 行动不超过 8 个；
   - 没有占位词、原始字段或虚构负责人。
9. 诊断审核失败时，只把失败行与对应事实交给 LLM 重写 1 次。第二次仍失败就停止
   交付，不能退回数据搬运版。
10. 生成 XLSX：

   ```bash
   /usr/bin/python3 <install_path>/scripts/build_xlsx.py \
     --input <OUTPUT_DIR>/diagnosis.json \
     --output <OUTPUT_DIR>/数据参谋平台分析会_<开始日期>_<结束日期>.xlsx
   ```

11. 补采、修正周期或重写诊断后，必须在当前 Run 重新构建并校验 XLSX。

如果运行环境支持独立诊断 Agent，可以用全新上下文执行第 7 步，降低主 Agent
预设结论的影响；不管是否使用独立 Agent，都必须完成一次明确的运营专家 LLM
诊断，不能直接渲染 facts package。

## LLM 诊断要求

- 指标只作为证据，不是结论。
- 单一证据只能写成“优先验证的原因”，不能强行写成确定因果。
- 本店表现与同行、上期或目标比较时，说明差异为什么影响询盘、订单、商品承接或
  资源分配。
- 国家、商品、关键词和访客动作要落到具体承接对象，但相同根因必须合并。
- 行业机会通常是 30d/90d 背景，不得伪装成精确一周店铺结果。
- 不写“加强运营、优化商品、提升转化、继续关注”等空话。
- 解决方案必须回应同一行的核心原因，并给出复查标准。

## 负责人和缺失字段

- `owner_name` 只能复制事实包真实返回的姓名。
- 无姓名时：
  - 店铺、商品、流量、广告、关键词、渠道动作写 `运营`；
  - 询盘、客户、报价、访客跟进写 `业务`；
  - 无法可靠归类时，省略负责人字段。
- 获取不到、为空或不影响结论的字段直接删除。
- 只有缺失数据直接阻断经营判断时，才在首页底部写一条业务化“数据限制”，最多
  3 句。
- 最终 XLSX 不显示 `未返回`、`待确认`、`不可判断` 或技术性覆盖清单。

## XLSX 结构

默认生成 `outputs/数据参谋平台分析会_<YYYY-MM-DD>_<YYYY-MM-DD>.xlsx`，
固定只包含：

| Sheet | 内容 |
|---|---|
| `经营结论` | 一句话结论；最多 3 个“发生了什么、核心原因、解决方案、复查标准”。 |
| `经营问题诊断` | 最多 15 个合并问题组；每行都有关键证据、专家判断、原因和方案。 |
| `行动与复查` | 最多 8 个根因级动作；负责人只显示真实姓名、运营、业务或省略。 |

不创建数据附录、数据覆盖、账号赛马、商品手术台、访客清单等独立 Sheet。
这些数据只能作为 LLM 诊断证据保存在 JSON 中。

## fallback

- 子类目排行遇到 NaN 时先换已验证参数组合；仍失败则记录为平台数据异常，不阻断
  其他模块诊断。
- 类目推断与店铺真实主营类目冲突时，以店铺真实类目或用户确认类目为准。
- 访客明细量大时只抽有 TM/询盘、高停留、高 PV、重点国家或高历史行为的代表样本。
- 只有平台机会、没有本店承接证据时，只写“需要验证的机会”，不能直接建议上新。

## 禁止动作

- 禁止调用发送、修改、保存、发布、上传、扣费、广告编辑或图片生成工具。
- 禁止创建、暂停、删除或调价广告计划。
- 禁止在最终 XLSX 暴露凭据或系统内部实现。

## Excel 安全与交付

构建器必须完成 LibreOffice headless 重存、清理 table/drawing 残留，并通过
`unzip -t`、`openpyxl.load_workbook()` 和包内残留扫描。任一步失败都不交付。

最终回复：

```markdown
已生成：[数据参谋平台分析会_<周期>.xlsx](outputs/数据参谋平台分析会_<周期>.xlsx)

老板结论：<diagnosis.executive_conclusion>
本周行动：<actions 数量及最重要动作>
数据限制：<只有确实影响判断时才写>
```
