# 国际站询盘复盘与行动闭环

本技能为老板、销售主管和管理者自动完成一次阿里国际站询盘复盘，并输出会后结果 `.xlsx`。运行完成后，管理者应能直接看到本周询盘健康度、最大风险、责任人、整改要求和下次复查方式。

## 核心原则

- 只使用真实返回的数据；客户、业务员、指标、国家、询盘内容、会话内容和跟进状态都不能编造。
- 数据为空、权限不足、工具失败或周期不完整时，写"未返回"、"不可判断"或"仅覆盖已获取日期"，不要补示例值。
- 工具名、JSON 字段、入参、原始错误码和采集细节只供 agent 内部执行；最终 XLSX 正文不得出现这些技术内容。
- 默认站在老板/管理者视角回答：谁风险最大、哪些高等级客户要盯、问题属于能力/态度/流程/分配哪一类、谁负责改、下次怎么验收。
- 禁止调用任何会发送、修改、发布、上传、扣费、发品或改变配置的工具。
- 缺数据也要尽量生成工作簿，但必须在 `本次会议总览` 和相关业务 sheet 写清缺口与影响。

## 时间范围

| 用户说法 | 周期 |
|---|---|
| 本周、这周、周五开会、本周询盘会、询盘分析会、询盘复盘会 | 本周一 00:00:00 至当前时间 |
| 上周、开上周询盘会、准备上周复盘 | 上一个完整自然周，周一 00:00:00 至周日 23:59:59 |
| 最近 7 天、近一周 | 滚动最近 7 天 |
| 今天 | 今天 00:00:00 至当前时间 |
| 昨天 | 昨天全天 |
| 最近 N 天 | 用户指定的最近 N 天 |
| 明确日期区间 | 严格按用户日期 |

用户没有给具体时间但表达的是询盘分析会时，默认用本周至今。

## 只读工具

执行前先用 Accio 当前可用的工具发现入口确认工具是否存在，不凭记忆调用。若目标只读工具不可用，继续生成 XLSX 框架和数据缺口说明，不假装已采集。

### 必采工具

| 工具 | 用途 |
|---|---|
| `subaccount_query` | 获取业务员/子账号清单；失败时用账号诊断返回的人员信息降级。 |
| `query_seller_acct_dim_diag_data` | 按日采集业务员维度沟通买家数、5 分钟回复率、回复时长、深度沟通、已读未回等。 |
| `query_seller_shop_dim_diag_data` | 按日采集店铺维度询盘接待总览，只用于管理层大盘。 |
| `query_seller_chat_quality_check_detail` | 按日采集具体质检问题，如已读未回、超 12 小时、仅打招呼、回复过短、重复回复、未跟进。 |

账号和店铺诊断均使用按日参数；不要用按周查询替代。今天或昨天数据未就绪时，写明缺口。

### 补充工具

| 工具 | 触发条件 |
|---|---|
| `query_recent_conversation`、`query_conversation_msg` | 用户点名业务员/客户，或质检明细暴露 P0/P1 重点询盘时，按目标会话补证据。不要全店遍历。 |
| `query_im_card_info` | 会话里出现卡片且语义文本不完整时解析卡片。 |
| `findCustomerShopInfo` | 需要公司/主营背景或高频询盘词作为管理背景时使用。 |
| `query_contact` | 需要补联系人、国家、aliId/loginId 或去重辅助时使用。 |
| `get_buyer_basic_info` | 需要补买家层级、国家、画像、历史浏览以判断重点询盘优先级时使用。 |
| `queryTradeListMcp` | 只有会话出现订单、付款、合同、交易卡片等线索时，只读核实询盘是否转订单；不要扩展成订单专题。 |
| `query_seller_knowledge` | 需要判断业务员回复是否缺专业信息时，用买家问题检索可补答内容。 |
| `get_seller_basic_info` | 只用于公司和主营背景，不生成店铺经营诊断。 |

不要把 `reply_buyer_over_30_days`、自动跟进配置、询盘任务工具、拦截项工具写入主流程，除非用户另开专题且工具已验证适用。

## 执行流程

1. 解析复盘周期、指定业务员、指定客户和输出目录。能按时间范围表确定时不要追问。
2. 串行采集同类按日数据，单个日期或工具超时只重试一次；不要因为局部失败停止整份工作簿。
3. 先采业务员和账号诊断，再采店铺总览，再采质检明细；只对重点询盘补会话详情、联系人和买家基础信息。
4. 将事实转成“复盘与行动闭环”JSON。此步必须由 agent 先完成内容诊断：逐条根据会话摘要、客户意图、负责人动作和证据完整度写出业务员点评、重点询盘逐条分析、共性归因、会议提问、下周动作和会后追踪项。
5. 用读取 `$alibaba-inquiry-meeting` 返回的 `install_path` 调用 `<install_path>/scripts/build_inquiry_meeting_xlsx.py` 生成 XLSX。脚本只负责渲染、格式和质量拦截，不负责替 agent 套规则写判断。
6. 如果脚本提示 AI diagnosis quality failed，必须回到 JSON 诊断步骤重写内容，不能交付带模板句、占位句或公式化判断的 XLSX。
7. 最终只回复文件路径、周期、管理风险数量和整改动作数量，不展开原始采集过程。

## XLSX 工作簿

默认输出 `询盘分析会_<YYYY-MM-DD>_<YYYY-MM-DD>.xlsx`，固定包含这些 sheet，不创建 `数据质量检查` sheet：

| Sheet | 内容 |
|---|---|
| `本次会议总览` | 周期、会议对象、会议范围、数据源覆盖、状态、说明、会议焦点和管理结论。 |
| `本周询盘概览` | 大盘买家、L1+、行业均值、Top20% 门槛和会议判断。 |
| `业务员询盘复盘` | 按人列出本周表现、典型询盘/证据、会议点评、需追问和下周改法。 |
| `重点询盘逐条分析` | P0/P1/P2 买家、等级、国家、负责人、问题、真实证据、会上确认和建议下一步。 |
| `共性问题归因` | 响应慢、未问清需求、报价前信息不足、跟进断档等共性问题的证据、归因和下一步。 |
| `管理复盘追问` | 面向全团队、具体业务员和重点询盘的证据追问、已经形成的结论或待负责人确认项。 |
| `下周跟进行动表` | 优先级、动作、负责人、客户/询盘、截止和验证方式。 |
| `会后追踪项` | 下次会议如何验证改善结果和当前状态。 |

数据缺口只写入 `本次会议总览` 和相关业务 sheet，不单独创建数据质量 sheet。

## AI 诊断要求

不要用固定公式替管理者做判断。L1/L2/L3、回复时长、已读未回、质检标签只能作为信号，不能直接套模板生成结论。

生成 `复盘判断`、`管理判断`、`责任动作` 和 `整改要求` 时，必须先读真实会话摘要、买家等级、客户意图、业务员回复内容和已有跟进结果，再用自然的管理语言回答：

- 这个客户或业务员当前真正的问题是什么。
- 这是能力问题、态度问题、流程问题、分配问题，还是数据不足暂时不可判断。
- 这件事对老板意味着什么风险：高意向流失、报价窗口错过、负责人不清、主管没有接力、话术无法推进需求等。
- 下一步谁负责做什么，做到什么程度，下次复查时看什么证据。

可以用优先级辅助排序，但不要写成质问式口号、固定小时数派单、重复留痕要求这类模板。自然表达示例：

- "买家已表达明确采购意图，但会话停在基础确认，没有形成报价、样品或下次沟通安排；需主管确认是否由原负责人继续推进，还是转给更熟悉该品类的人接手。"
- "该业务员接待量不低，但高等级客户的连续跟进弱，问题更像跟进节奏和优先级管理不足，而不是单纯接待量不够。下次复查应看重点客户是否都有明确下一步。"
- "当前只看到质检标签，缺少完整会话内容，不能判断是漏看、话术能力还是客户自然沉默；先列为待复查，不做人员定性。"

整改动作必须具体，但语气要像管理复盘结论，不要像机器人派单。每条动作至少包含负责人、客户/询盘、完成口径、截止时间或复查时间、复查证据。不要只写"加强沟通"、"提升回复速度"这类空话。

## 安全与交付

- 不要调用 `send_msg`、`send_*`、`set_*`、`update_*`、`save_or_update_*`、`batch_edit_product`、`publish_*`、`oss_upload_file`、`consume_ipoint`、`image_generate`、`image_edit`。
- 用户要求直接发消息或改配置时，只能生成待人工确认的整改动作，放入 `下周跟进行动表`。
- 交付前必须由脚本完成：LibreOffice headless 重存、清理 table/drawing 残留、`unzip -t`、`openpyxl.load_workbook()`、包内残留扫描。
- 任一步失败都不要交付 XLSX，先修复后重新生成。
